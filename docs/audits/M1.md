# Audit M1: architecture documents (task T-M1-06)

Auditor: role E (independent; wrote none of the six documents). Date: 2026-11-13.
Scope: `docs/ARCHITECTURE.md`, `TECHNICAL_DECISIONS.md`, `IMPLEMENTATION_PLAN.md`, `AGENT_TASKS.md`, `TEST_STRATEGY.md`, `RISK_REGISTER.md`, read against `docs/PROJECT_BRIEF.md` and `AGENTS.md`.
The documents were re-read after the coordinator's ADR-015 (local-only CI) edits; the reference checks below ran on the post-edit text. GitHub Actions items are not reported as gaps, per the coordinator's instruction. The new text is checked for consistency (section 1 and fix list).

## 0. Verdict

**ACCEPT WITH FIXES.**

The id graph is sound, the safety design (probe before mount, `norecover`, banned options, read-only descriptor) matches what the NTFS-3G source does, and the key feasibility and durability limits are quoted correctly from macFUSE 5.5.0. No claim that decides feasibility was contradicted.

Four problems must be fixed before M2 starts, because they touch data safety or security:

1. Untrusted volume label flows into the root daemon's mount option string and mount path (challenge C1).
2. The host journal has no defined way to be cleared after Windows `chkdsk` or `ntfsfix`, so a volume that was once unclean stays read-only forever (C2).
3. The only on-disk marker (ADR-006 phase 2) is described as optional, yet the source shows NTFS-3G never sets the dirty flag, so guarantee D3 and the "unclean detach" story do not hold without it (C3).
4. Guarantees D1 and D2 are worded beyond what their sources and mechanisms support (C4, C5).

Several `[V]` claims are stronger than their sources (section 3). The rest are editorial fixes.

## 4. Challenges (data corruption, security, over-claiming)

**C1. Option and path injection through the volume label (security, high).** ARCHITECTURE section 3.3 passes `volname=<label>` inside one comma-separated `-o` string, and section 4.1 step 7 creates `/Volumes/<label>` as root. The label comes from the attached disk, which is hostile by the document's own threat model. A label such as `X,remove_hiberfile` or `X,allow_other` or `../../etc/x` is not covered: section 6 says "client-supplied strings are limited to `bsd` and `mode`" but the label is not client-supplied. The probe (parser of hostile data) also returns the label as JSON text to the root daemon. The ADR-005 unit test ("no input yields `recover`") only tests the option builder inputs it is given. Fix: the builder must treat label as data, never in the same string as options (use an escaped form or a fixed `volname` derived from a sanitised label: allow-list of characters, length cap, no `,` `/` `\0`), validate the final argv by parsing it back against the allow-list, create the mount point with `mkdir` on a validated leaf name using `O_NOFOLLOW`/`openat`-style calls, and fuzz the JSON parse in the daemon.

**C2. Journal deadlock after repair (data safety / usability, high).** ARCHITECTURE section 3.5 removes a journal entry only when a worker exits 0 after an unmount request. Policy row 2 forces `ro` whenever the journal says "left open", and tells the user to run `chkdsk` on Windows. `chkdsk` clears the on-disk dirty flag but cannot touch the host journal; the volume then probes `clean`, the journal still exists, and the policy stays `ro` forever, because a read-only session can never produce the "clean read-write unmount" that removes the entry. `ntfsmac repair --clear-dirty` does not mention the journal either. Define an explicit, typed-confirmation journal clear (and say what evidence it requires, for example probe `clean` and an unchanged serial), plus a test (G6). Also note the journal key (volume serial) is shared by clones and images; two copies of one image will share state.

**C3. D3 and the unclean-detach story depend on a phase that is optional on paper (data safety, high).** Source (section 2 row 16) shows NTFS-3G does not set `VOLUME_IS_DIRTY` and, per the man page and code read, does not write `$LogFile` state either. So after a surprise removal, nothing on the disk says "unclean". ADR-006 makes the on-disk marker conditional ("if NTFS-3G already sets and clears the flag, phase 2 is dropped") and gates it on T-M3-12, an Opus task marked "conditional". Meanwhile ARCHITECTURE section 9 D3 states as a guarantee that such a volume "is flagged dirty for Windows", and section 7 says "On Windows the dirty flag triggers a `chkdsk` prompt". Until the marker exists, D3 is false for any volume moved to another machine. Fixes: make phase 2 the default plan (drop it only if T-M3-01 proves the opposite), mark D3 "host-only until T-M3-12 passes", and fix the wording in section 7.
Related: the marker step uses `libntfs-3g` to open and write `$Volume` (T-M3-12, `src/volmark/`). That is NTFS parsing in a write-capable process. It is missing from the ARCHITECTURE component table and section 3 claims "the daemon never parses NTFS metadata". State its uid, sandbox, and descriptor (it must run in an unprivileged sandboxed helper like the worker, with an `O_RDWR` fd only after policy says `rw`).

**C4. Guarantee D2 is worded too strongly (over-claim).** "A volume that policy classified as unsafe is never written, even if the NTFS parser misbehaves." The classification itself is produced by the probe, which is the NTFS parser. A probe bug or exploit that reports `clean` for a dirty or hibernated volume leads to an `O_RDWR` descriptor. What the descriptor mode really guarantees: a *correct verdict of unsafe* cannot be overridden by a later parser bug in the worker. Reword D2 and add the second line of defence that does exist (the engine's own checks with `norecover`; `hiberfile` EPERM fallback), and test it (G7). Also note `hiberfil.sys` header `wake`/`WAKE` and other hibernation states are not recognised by the engine either (the source checks only `hibr`/`HIBR` and size), so a Windows resume-in-progress state is classed as safe.

**C5. Guarantee D1 relies on unproven mappings (over-claim).** D1 says every byte written is on the device after a successful eject or unmount. The chain needs (a) FSKit to flush its buffer cache to the module on unmount, (b) the module to deliver `FUSE_FLUSH`/`FSYNC`/`DESTROY` for all dirty files, and (c) errors in that last flush to be visible. Section 4.4 admits (a) and (b) are assumptions, and source S1 says flush errors on macOS 27 are logged and dropped. D1 is correctly conditioned on "once the tests pass" in the text, but the table presents it next to the proven items. Move D1 under "tested guarantees only after T-M2-06", and require that unmount success be reported to the user only if the worker saw zero write or flush errors.

**C6. "The daemon marks the session failed after the first write error" has no mechanism.** The worker is stock `ntfs-3g`; the daemon only sees its exit status, stderr and the DA events. There is no channel in the patch list (0001 to 0005) or in the interfaces that reports a device write error or a flush error to the daemon. Either add a small patch (reported through the exit code, a file descriptor, or a log line the daemon parses) or remove the claim from sections 7 and R-05.

**C7. `ntfsmac repair --clear-dirty` can hide real damage.** `ntfsfix -d` clears the flag without checking consistency. The document says it is only suggested late and needs a typed label, but it does not restrict when it runs: it should be refused unless the probe state is exactly `dirty_flag` (no unclean log, no hibernation, no `fast_startup`), and it must also remove the journal entry (C2). It also must not be used on a volume that the journal says this product left open without an additional warning, because then the missing writes are ours.

**C8. `fmask=0133` removes the execute bit for every file.** This is a conservative security choice but a functional change: scripts and binaries on an NTFS volume cannot be executed, and `chmod +x` is silently ignored or fails depending on the backend. It is not mentioned in section 9 limitations, the I-FUNC cases, or the user messages. Add a test (G1) and a documented limitation.

**C9. Sandbox is [A] and the fallback is "drop to uid separation".** Acceptable as an honest statement, but R-07's likelihood and residual-risk text assume the sandbox. The release readiness report should say "sandbox verified" or "not verified" explicitly. Also the worker needs the Mach service `io.macfuse.mount` and, depending on FSModule behaviour, more; do not claim "no network, no exec, access limited to the inherited fd" before T-M4-06.

**C10. Root daemon and mount-approval dissenter.** A crash or hang in the daemon while a dissent callback is pending can block automount of every NTFS volume and potentially of other volumes the filter matches (`whole-disk media` is in the filter in section 4.1 step 1). Add a watchdog, answer the callback only for disks that passed the NTFS content filter, and test that a daemon restart does not leave volumes unmountable (T-M4-05 covers restart reconciliation but not callbacks).

**C11. Probe fd inheritance and `/dev/fd/N`.** Section 3.3 passes `/dev/fd/<N>` as the device. `ntfs-3g` checks whether the device is already mounted and reads size by ioctl. U5 lists this; note the additional risk that a second `open()` of `/dev/fd/N` with different flags does not exist on Darwin for read-only fds, so an unpatched worker may try `O_RDWR` and fail rather than fall back. T-M2-05 should test both `ro` and `rw` fds explicitly.
