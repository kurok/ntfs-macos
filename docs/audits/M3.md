## 2. Findings, by severity

No High finding. No finding shows a way for the current code to give a read/write mount of a volume that should be read-only or refused, or to lose data that was synced.

### Medium

**F-01. The production option set lets the worker daemonise, which breaks the supervision that ARCHITECTURE sections 4.1 and 7 build on** (`src/options/options.c:67-69`, `src/options/argv_check.c:38-41` and `:193-195`, `integration/mount-options.json` `always`, ARCHITECTURE 3.3 "Always" row; NTFS-3G `src/ntfs-3g.c` `setup_logging()` line 4330 (`daemon()` unless `no_detach`), called at line 4610 of the patched tree, after `mount_fuse()` (4596) and after patch 0006 writes `S` (4604)).
The option builder never emits `no_detach`, and `argv_check()` rejects it as an unknown key. Without it, `ntfs-3g` calls `daemon()` once the FUSE mount has been requested: the process the daemon spawned exits 0 at once, and the process that serves the volume is a new child that has called `setsid()`, so it has its own session and process group and its parent is `launchd`. Every test and spike that supervises a worker passes `no_detach` itself (13 places, for example `tests/integration/errfd/i_err.py:230-232`, `tests/integration/mmap/mmaplib.py:91`, `tests/integration/sync/dtrace_check.sh:57`), so the supervision rules below were never exercised in the production form. (`C-REF-OP-*` does mount with the builder's string, through `tests/compatibility/ref/optstr.c`, and only polls for the mount, which works with a detached worker.)
Consequences for the design as written:
- Section 7 rule 3 ("the daemon saw the unmount before the worker exited") and rule 5 (worker exit status 0) refer to a process that exits before the mount appears. Either every read/write session is judged unclean (the marker is never cleared and every volume comes back `dirty_flag` after its first session: fail closed, product unusable), or the daemon has to watch a process that is not its child and whose exit status it cannot collect.
- Section 4.1 step 8 and 3.3 send `SIGKILL` "to the worker's process group" on the 30 s deadline. After `setsid()` the serving process is not in that group, and it ignores `SIGTERM` (T-M2-03). Failure scenario: FSKit is slow to show the mount; the deadline passes; the daemon kills the (already empty) group, records the attach as failed and closes its descriptors; the detached worker still holds the inherited `O_RDWR` device descriptor and its mount appears later, unsupervised (no channel reader, no unmount handling, no `volmark clear`; the journal entry says the session failed). A re-attach can then put a second writer on the same device. This is a data-loss path once T-M4-01 is implemented to the letter of the spec.
- ARCHITECTURE 3.4 check 2 (peer's process group or parent chain reaches a spawned process) does not recognise the detached worker. Checks 3 and 4 and the sandbox still hold, so this is defence in depth only.
Fix (recommended now, it is three small edits in M3-owned files): add `no_detach` to the Always row of ARCHITECTURE 3.3, to `integration/mount-options.json`, to the builder's literal and to the mandatory set of `argv_check()` rule 6, with `U-ARGV-*` and `U-POL-*` updated; state in 3.3 that the spawned process is the serving process; re-run `I-ERR-03` and `I-SMOKE-01` with the option string from the builder. If the owner prefers the daemonised form, sections 4.1 step 8 and 7 must instead say how the detached process is found, killed and its end observed, before T-M4-01 starts.
Status: verified by reading the patched NTFS-3G source, the builder, `argv_check()` and the tests; not run in the daemonised form.

### Low

**F-04. The policy trusts `state` and `reason_codes` alone for `rw`** (`src/policy/policy.c:40-43`, `:78-88`).
`ntfsmac_policy_decide()` returns `rw` for `state: clean` with no reason code, whatever the other fields say; the verdict parser (`src/sanitize/verdict.c:139-180`) enforces only the cross-field rules of section 3.1. A verdict `clean` with `logfile: unclean`, `hiberfile: hibernated`, `bitlocker: true`, `is_ntfs: false` or `volume_flags: ["DIRTY"]` would therefore be mounted read/write. The probe cannot produce such a verdict (its state is derived from the codes and every such field is set together with its code), and a compromised probe can lie consistently anyway, so this is defence in depth: the worker still refuses an unclean log or a `hibr` file, and `volmark set` refuses `DIRTY`. Fix: in `verdict_is_clean()` also require `is_ntfs`, `!bitlocker`, `logfile` `clean`, `hiberfile` `absent` or `inactive`, `has_ntfs_version`, and `volume_flags` within the informational bits; add the inconsistent verdicts to `U-POL-FAILCLOSED`.

**F-05. The `hiberfil.sys` header rule treats every unknown signature as an inactive file** (`src/probe/names.c:348-358`).
Only `hibr`, `HIBR`, `wake` and `WAKE` (and a file shorter than 4096 bytes) give `hibernated`; any other first four bytes give `inactive`, which is `clean`. Windows' power manager also uses other image signatures (for example a link or break-in signature) and, as far as this auditor knows, writes zeros over the header once a resume has finished; NTFS-3G's own comment says "all header bytes are zero" for the safe case. A volume whose hibernation file carries a signature not in the list would be mounted read/write. Unverified against real Windows output (needs Environment C, H6). Fix: classify `inactive` only when the first 4 bytes are zero (or another value shown by `H-USB-*` to be inactive), and `hibernated` for anything else; this only ever moves volumes towards `ro`. Add a fixture with an unknown signature.

**F-06. `volmark set` accepts `CHKDSK_UNDERWAY` and the pending-work flags** (`src/volmark/args.c:128-133`).
`set` refuses only `DIRTY` and bits outside `VOLUME_FLAGS_MASK`, while the probe's check 3 gives `dirty_flag` for 0x4000 and 0x0002/0x0004/0x0010/0x0020. Volmark is the last re-check before the first write of a session; if the flags change between the probe and volmark (a shared or re-attached device, a probe bug), a volume with `chkdsk` work pending would be marked and then written. Matches the spec (ARCHITECTURE 3.6 step 3), so this is a spec-level hardening: let `set` refuse every bit except the informational `MODIFIED_BY_CHKDSK` and `MOUNTED_ON_NT4` (exit 11), and update the 3.6 table and `U-VMK-10`.

**F-07. `removexattr` with an empty open-namespace name would remove the file's unnamed `$DATA`** (NTFS-3G `src/ntfs-3g.c` `ntfs_fuse_removexattr()`, line 3861 of the patched tree: `ntfs_attr_remove(ni, AT_DATA, lename, lename_len)` with `lename_len == 0`).
Patch 0009 adds the empty-name guard to `setxattr` only, and says in its header that without it the call "would address the unnamed data stream, that is the file content". `removexattr` has the same shape upstream. It is not reachable through the system call: on this host `removexattr(path, "", 0)` and `setxattr(path, "", ...)` fail with `EINVAL` before any file system sees them (auditor check on a scratch file; the macOS VFS validates xattr names), and Linux rejects empty names too. Unverified whether any FSKit path delivers an empty name. Fix (cheap, same scope as 0009): add the same `lename_len == 0` guard to `ntfs_fuse_removexattr` under `__APPLE__`, and mention it in the upstream report.

**F-08. Patch 0006 reports a short write that the engine then completes as an `E` record** (`third_party/patches/ntfs-3g/0006-session-channel.patch`, `ntfsmac_unix_io_pwrite`/`_write`; NTFS-3G `libntfs-3g/device.c` `ntfs_pwrite()` lines 277-290 loop until the whole buffer is written).
A device that returns a partial count once makes the session unclean although nothing failed. Fails closed (a read-only next attach and a `chkdsk` message), never towards data loss, and rare on real devices. Fix: document it in the patch header and ARCHITECTURE section 7 (`E` means "a device call failed or was short"), or report only `res < 0` and let the engine's own error reach `E` through `ntfs_umount`. No change needed for the gate.

(a) 3.5 and 3.8 cite `tests/results/2026-11-15-a09b94d-B.json` for `I-BIG-02/-03` and `I-READ-01..07`; that file holds only `I-MMAP-*`. The cases are in `2026-11-15-bced1be-B.json`. ### 3.2 Policy, option builder, `argv_check()`

Every row of ARCHITECTURE 3.2 is implemented as written (`policy.c:61-132`): `rw` only for `clean` with no reason code, no journal entry and `mode=auto`; every out-of-range input takes the `unknown` row (`ro`); `mirror_split`, `corrupt`, `unsupported` are `refuse`. The gates match their table rows (the repair gate excludes `unknown`-class codes explicitly, as the comment explains).

`recover`, `remove_hiberfile`, `fsname` and every other banned key cannot be emitted: the builder writes only string literals and two numbers (`options.c:65-102`), and nothing from the disk enters the option string (the leaf is a separate argument). `argv_check()` independently rejects banned and unknown keys, duplicates, empty tokens (also a leading or trailing comma), any byte outside `0x21..0x7E` and `\`, and requires `norecover` and the rest of the Always row (rule 6). `ro` is required if and only if the decision is `ro`, and rule 7 checks the descriptor's access mode. The only gap found is the missing `no_detach` (F-01).

### 3.3 Sanitisers and verdict parser

`label_cp.c` decodes strict UTF-8 (no overlongs, surrogates, C0/C1 lead bytes or code points above U+10FFFF) and uses an allow-list: ASCII letters, digits, space and `-_.()+` only, so `/`, `,`, `=`, `\`, `:` and control bytes never pass; the non-ASCII deny table is generated from Unicode 15.1.0. The label sanitiser falls back to `NTFS-<serial>` when nothing original survives; its output always satisfies `ntfsmac_label_part_ok()`, which `argv_check()` rule 2 applies to the leaf. The path display sanitiser escapes everything else as `\u{...}` / `\x{..}` (ESC, bidi controls and `\` included). Journal file names are built only from the parsed 64-bit serial. Disk-derived strings therefore reach neither a file name, nor the option string, nor a terminal unescaped. Host ctest: `sanitize.label`, `.display`, `.verdict`, `.verdict_schema` and the three seed replays pass.

### 3.5 Journal and volmark ordering

Journal (`src/journal/journal.c`): temporary file `O_CREAT|O_EXCL|O_NOFOLLOW`, written, `F_FULLFSYNC` (fallback `fsync` only for `ENOTSUP`/`EINVAL`/`ENOTTY`), closed, renamed (`renameatx_np(RENAME_EXCL)` / `renameat2(RENAME_NOREPLACE)` for a new entry, atomic replace for an update), directory synced; removal renames into `cleared/` and syncs both directories. Marker transitions only `pending` to `set` or `failed`; state only `open` to `write_error`; the clean-session removal requires `state=open` and `marker` `set` or `none`. A crash at any point leaves either the old or the new entry, never none: confirmed by `journal.crash` on the host (macOS, real `F_FULLFSYNC` and `renameatx_np`) in this audit.

Volmark (`src/volmark/volmark.c`): step 1 mounts read/write with `NTFS_MNT_FORENSIC` only, re-runs the hibernation and log refusals and the size check; step 2 binds serial and sector count from sector 0; step 3 decides from the raw flags; `w` is printed (and catchable signals blocked, the pre-write alarm cancelled) before the only write, `ntfs_volume_write_flags()`; a failed write is not repeated (the inode is marked clean before the unmount); step 5 `fsync` then the drive flush; step 6 a read-only mount reads the flag back and compares records 0 to 3. `ntfs_mft_records_write()` writes `$MFT` (W1) before `$MFTMirr` (W2) from a copy taken before W1, so a W1-W2 cut always gives `$MFT` ahead by one USN.

Crash table of ARCHITECTURE 3.6, reproduced at `a983be6` with the fault layer (156-case sweep, `tests/results/evidence/2026-11-15-a983be6-audit/volmark/volmark-evidence.txt`), for `set`, `clear` and `clear-repair`, each with and without a kill:

| Row | Observed |
|---|---|
| Before step 4 | 0 device writes before `w` (count plan); `SIGKILL` before step 4: image unchanged, probe gives the old state |
| Inside W1 | `short:1:K` for K = 256 to 1022: `$MFT` record 3 torn, probe `corrupt` |
| Between W1 and W2 | `cut:1`, `short:1:1023`, `short:2:0..2`, `skip:2`: `$MFT` ahead, probe `mirror_split` |

Every row gives the stated outcome; no cut gives `clean` with the flag lost while a session was open, and the worst outcome inside step 4 is `refuse`. The daemon ordering of 3.6 (journal `pending` and synced before the device is opened `O_RDWR`, `set` before the worker, `clear` only after the positive proof, entry removed only after `clear` exits 0) has no window in which the flag is clear, the entry is gone and the session was unclean. Its implementation is M4 (T-M4-14); F-01 affects the "positive proof" it depends on.
