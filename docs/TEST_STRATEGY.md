# Test strategy

Source tags `[V:Sn]`, `[A]`, `[U]` are defined in [ARCHITECTURE.md](ARCHITECTURE.md). Acceptance thresholds are in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) section 2.

## 1. Principles

| Principle | Consequence |
|---|---|
| Data corruption is release-blocking. | Every write test ends with a hash comparison after unmount and remount. A mismatch stops feature work. |
| Linux results say nothing about macOS. | Each test id is tagged with the environment that ran it; the status table never promotes a Linux result to "Verified (VM)". |
| No destructive test on the developer host. | The host builds, runs unit tests and drives VMs. It never mounts an NTFS image: Paragon NTFS on the host claims `Windows_NTFS` volumes with probe order 1 and would mount any attached NTFS image itself [V:S17]. |
| A test that cannot fail is a defect. | Each integrity test has a negative control (a deliberately corrupted byte must make it fail). Agent E checks this in the M5 audit. |
| Images are disposable and synthetic. | Fixtures are generated, never copied from real disks. Fuzz inputs come only from generated images. |

### What the VM cannot show

| Gap | Why | Covered by |
|---|---|---|
| Real USB insertion and surprise removal | Virtual disks do not hot-unplug like USB. macOS 27 adds USB accessory passthrough to guests [V:S23]; tool support is [U]. | Environment C; in B, a force-detach of the image approximates it |
| Drive write-cache behaviour, `DKIOCSYNCHRONIZE` and `F_FULLFSYNC` honesty | Virtual disk backed by host file cache; `DKIOCSYNCHRONIZE` returning 0 on a virtual disk proves nothing about a drive (T-M3-10) | Environment C |
| Sleep/wake with a mounted volume | Guest sleep is not representative | Environment C |
| Coexistence with Paragon or other NTFS drivers | Not installed in the guest; a dummy bundle tests only the detection logic | Environment C, only if the human chooses (H7) |
| Kernel backend | Kexts do not load in VMs [V:S3] | Not in scope (ADR-001) |
| Whether FSKit extensions work in a guest at all | Resolved: they do (U2, T-M2-02) | Environment B |

## 3. Fixtures

All fixtures are generated in Environment A by scripts under `tests/fixtures/gen/` from a seed; images are not committed. Every fixture image has a volume serial number of its own: the first 8 bytes of SHA-256(`ntfs-macos fixture serial: ` + the fixture name), little endian, written by `tests/fixtures/gen/setserial.py` into the primary and the backup boot sector before export (right after `mkntfs` in clean.sh, unsafe.sh and names.sh; after the workload for the mirror and sweep images; after the cut for the vmk images; labels.sh gives each label image the serial of clean-64m-4k plus a multiple of its index) (nothing else changes). The reason: the daemon's session journal is keyed by the volume serial, and `mkntfs -T` (fake time 0, needed for reproducible images) fixes the serial too, so every fixture used to carry `0x34F5EE1202469FF7`. Two fixtures attached together (`clean-64m-4k` rw and `dirty-flag` ro) then shared one journal entry, and whether `dirty-flag` probed as `dirty_flag` or as a volume this Mac left open (`dirty_flag_journal`) depended on the order of the probes. A new generator must call `setserial.py` too. `tests/fixtures/manifest.json` lists name, generator, seed, size and the SHA-256 expected after generation.

Mount hygiene of the mmap suite (`mmaplib.Worker.start()`): macFUSE 5.5.0 on the FSKit backend can refuse a volume (`MFMount: ... Failed to initialize volume`; the worker stays alive and nothing mounts) when a mount follows a clean unmount of the previous volume on the same directory within a second. Before every mount the worker waits, with a 30 s deadline, until `/sbin/mount` has no line for the mount point and none for a device earlier workers had on it; this catches leftover or forced mounts, and a wait that is not clear at the deadline errors the case (`WaitTimeout`). It then settles 1 s and logs how long the wait took. The settle and a single retry deal with the FSKit timing race itself: when the output has the refusal, the worker is killed and checked dead, its output is kept as `<ID>.worker-refused-<tag>.log`, and the mount is tried once more after the same wait. The retry goes into the result note of the case (first error line, whether the worker was still running when killed) and into `observations.json`. A second refusal, a wait timeout and any other mount failure fail the case as before; `verify_image` turns an ordinary mount failure into an observation but re-raises a refusal and a wait timeout. Host-side tests: `tests/unit/harness/test_mmap_mount.py` (run by `harness.unit`).

Purpose: show that running the same engine behind macFUSE FSKit does not change on-disk results.

4. Both resulting images are dumped in Environment A by `tests/tools/treedump` (links `libntfs-3g`, read-only): path, type, size, allocated size, SHA-256 of the unnamed stream, each named stream with its hash, NTFS times, file attribute flags.

## 6. Crash, kill and disconnect testing

| Technique | Environment | What it proves |
|---|---|---|
| Crash-consistency sweep (below) | A | State of the image if the device stops accepting writes after write N, for many N |
| `SIGKILL` of worker during copy | B | Daemon cleanup, journal, read-only on next mount, no hang of applications (`daemon_timeout` is not relied on: T-M2-04 found an explicit value ignored) |
| `SIGKILL` of `ntfsmacd` | B | Open files keep working; restart reconciliation |
| Kill of the macFUSE FSModule process | B | Volume failure mode and cleanup [V:S7 describes the mode] |
| Force-detach of the disk image during write (`hdiutil detach -force` in guest, or removing the virtual disk) | B | Approximation of unplug |
| Real unplug during write | C | The real thing |
| Guest hard power-off during write (`tart stop` without shutdown) | B | Power-cut approximation; journal survives; next boot mounts read-only. A plain `tart stop` is not a clean shutdown: files written seconds before it were missing after the next boot (T-M2-02), so `vm/macos/tart.sh stop` syncs and shuts the guest down first, and no durability test may treat a plain `tart stop` as clean. Its use as a power cut is an approximation only: which layer loses the data (guest page cache, virtual disk, host cache) is not measured, so it is not shown to be equivalent to a power cut |

After every scenario the checks are the same: (1) the next attach mounts read-only with the documented reason, or is refused as `mirror_split` (classified window below; D3 exception); (2) every file that had been synced before the event (the test records these) has the right hash; (3) `ntfsfix -n` reports no fatal error, which means exit 0, or exit 1 on a point classified `mirror_split`; (4) in Environment C, `chkdsk /scan` output is stored; (5) once T-M3-12 has passed, the image carries `VOLUME_IS_DIRTY`.

`ntfsfix -n` is a shallow check (boot sector, `$MFT` against `$MFTMirr`, `$LogFile`; it never walks indexes or run lists), and it is not a pure reader: it prints "Correcting differences in $MFTMirr ... OK" and "Going to empty the journal ... OK" without writing (image hash unchanged), and its final step is a read/write `ntfs_mount` (`ntfsfix.c:1649`), whose failure gives its exit 1. Its text is never evidence of a repair [V: T-M3-14 triage].

### Crash-consistency sweep

Patch 0004 adds a device-operations wrapper inside `libntfs-3g`, compiled only with `--enable-faultio` (release objects proven identical to a build without it by `nm` and `objdump`, `tests/results/evidence/m314/full/build-proof.txt`). `write()` and `pwrite()` share one write counter. Environment variables (all ignored when `NTFSMAC_FAULT_PLAN` is unset or empty):

| Variable | Meaning |
|---|---|
| `NTFSMAC_FAULT_PLAN` | The plan (table below). An unknown plan makes every write fail with `EINVAL` (fails closed). |
| `NTFSMAC_FAULT_KILL` | `1`: at the fault point the layer kills `ntfs-3g` with `SIGKILL` instead of dropping later writes. The sweep always sets it: dropping writes and reporting success let the engine read back stale metadata and spin in one trial, which no real power loss can do. |
| `NTFSMAC_FAULT_STATE` | File holding the running write counter, written before each device write; the workload reads it right after `fsync` returns, so a claim's write count is conservative. |
| `NTFSMAC_FAULT_TRACE` | File receiving offset, length and the first bytes (magic) of every write, including the one about to be dropped; the sweeper classifies `mirror_split` from it. |

| Plan | Effect (with `NTFSMAC_FAULT_KILL=1`) |
|---|---|
| `count` | No fault; reports the number of device writes at exit |
| `cut:N` | Writes 1..N reach the image; the process is killed before write N+1 is issued. (Without `KILL`: later writes are dropped and report success.) |
| `skip:N` | Write N alone is dropped; later writes go through: a reordering of persistence (supplementary) |
| `short:N:K` | Write N writes only its first K bytes, then the kill (torn write; supplementary) |
| `eio:N` | Write N returns `EIO`; later writes succeed |
| `dead:N` | Write N and everything after returns `EIO` (unplug) |
| `delay:MS` | Every write is delayed (section 7) |

Fault model: the sweep's images are files, and the kernel keeps every issued write after `SIGKILL`, so writes persist in issue order. Real devices without a flush may persist any subset; `--plan skip` exercises one reordering, and neither it nor `--plan short` is part of 3.9.

Sweep (`tests/stress/crashsweep/run.sh --mode full`, Environment A): for each of 5 workloads (`seqwrite`, `smallfiles`, `renamechurn`, `overwrite_truncate`, `dirtree`), get the write count W with `count`, then run with `cut:N` for 110 values of N spread over 1..W (550 points; criterion 3.9 needs at least 500). Controls: the `count` run of each workload and `cut:0`, which must leave the image byte-identical to the fresh one (10 controls). After each run, with the release build and `norecover`: read-only mount, `ntfsfix -n`, the durability claims (every file whose `fsync` of file and parent returned at a write count up to N, unless a later operation on that path had started) and an advisory walk (`walk_dirty`, not a failure). `tests/stress/crashsweep/README.md` has the details.

A failing cut point is not automatically a project bug: NTFS-3G has no journal, so some windows of metadata inconsistency are inherent. Each failure is classified by the senior reviewer as (a) expected non-atomic window, documented in the limitations (ARCHITECTURE.md section 9), (b) engine defect, reported upstream, or (c) defect in our patches, release-blocking.

**Classified window `mirror_split` (class a).** A failing cut point is `mirror_split` only if all three hold; anything else stays an unclassified failure:

1. The read-only refusal and the `ntfsfix -n` message are exactly "$MFTMirr does not match $MFT (record k)." with k in 0..3, and nothing else failed.
2. The write trace shows that write N is `$MFT` record k and write N+1 (never issued) is `$MFTMirr` record k.
3. On a scratch copy with the mirror record replaced by the raw `$MFT` record, the read-only mount, `ntfsfix -n` (exit 0), every claim and the walk pass.

The product side of this window (probe state, refusal, `repair --sync-mirror`) is ADR-021 and ARCHITECTURE.md section 3.7.

**Gate (modes `short` and `full`, plan `cut`).** Exit 0 if and only if: controls 10 of 10; zero unclassified failures; zero broken claims; zero workload hangs. The `mirror_split` and `walk_dirty` counts are reported in `summary.json` and never fail the gate. No count is pinned: they follow NTFS-3G's write sequence and change with any engine or workload change, and the rule above already proves each point. Full run at 7174b4b: 550 points, 532 pass, 18 `mirror_split`, 0 of 15,626 claims broken, 0 hangs; short run: 250 points, 11 `mirror_split` (`tests/results/evidence/m314/`).

**Torn writes (`--plan short`, supplementary).** "Incomplete multi-sector transfer" on a torn 1 KiB MFT record or 4 KiB index block is the update-sequence protection working, not a defect. Without a journal the record cannot be redone, so a tear can make already synced data unreadable (204 failing points of 550 with `short:N:512`, 115 broken claim sets). Class (a); limitation N11 (ARCHITECTURE.md section 9).

## 9. Continuous integration (local only)

There is no GitHub-hosted CI: no GitHub Actions workflows, no hosted runners and no binaries uploaded to GitHub (ADR-015). All checks run on the developer Mac through `scripts/ci-local.sh`, which wraps `scripts/test-all.sh`. `scripts/test-all.sh --env host|A|B [--quick] [--cases GLOB] [--dry-run]` (T-M5-01) is the one command per environment: it runs every stage of the environment in order, continues after a failure, and writes one result file (section 10); `--env B` runs through `vm/macos/run-suite.sh`, whose stages are `guest-build`, `integration`, `compat`, `daemon` and one `stress-NAME` per registered entry. `guest-build` (`vm/macos/guest-build.sh`, full runs only; `--no-guest-build` is an option of `vm/macos/run-suite.sh`, which `test-all.sh` and `ci-local.sh` do not pass) is one clone that builds NTFS-3G and compiles, in the guest, every `cc` line of the VM scripts `tests/integration/daemon/{spawn,sandbox,errwatch,journal,dmn_mirror,xpc}_vm.sh` (the lists of `tests/unit/ci/check_guest_sources.py`, the lines that need libntfs-3g, macFUSE and the FUSE stand-in included, which `ci.guest_link` skips on the host): a missing header or a link error fails the run in its first minutes and every later B stage is then skipped ("guest-build failed"). Nothing is saved or shared between guests. Criterion 5.1 is met by three commands, one per environment that has tests: `--env host` (macOS build and unit tests, never a mount), `--env A` and `--env B`; the macOS unit tests run only in `--env host`. A missing prerequisite (docker, tart, `ntfsmac-golden`, the image `ntfs-macos-linux:release`, the pinned NTFS-3G tarball) fails the stage `preflight` and records every later stage as skipped; the script never builds an image or downloads anything (it names the command to run). A run in which no case passed exits non-zero. B runs take a VM slot lock (`${TMPDIR:-/tmp}/ntfsmac-vm-slots`, `--slot-dir` to override). A stress suite registers with a `tests/stress/NAME/run.sh` (environments in `NAME/ENVS`); none registered is a skipped stage. **Lanes of environment B.** After `guest-build` (alone, a failure blocks both lanes) a full B run uses its two VM slots at the same time, each lane one guest at a time: phase 2 `integration` then `compat` || `daemon` (about 2000 s || 1865 s); phase 3 `stress-soak` || `stress-kill` then `stress-leaks`; phase 4 `stress-parallel` || `stress-disconnect`; a stress entry that is not in this list runs alone afterwards. The pairing keeps the two heavy suites (soak, the mixed workload; parallel, 16 writers) from ever running together, and the deadline driven kill and disconnect suites from running together; each heavy or deadline suite shares the host only with a lighter one (the host has 18 cores, each guest 4 vCPUs). Measured on the last sequential run (guest-build 60 s, integration 1774 s, compat 226 s, daemon 1865 s, disconnect 286 s, kill 256 s, leaks 71 s, parallel 429 s, soak 718 s: 5685 s) the plan takes about 3200 s. `--lanes 1` (`test-all.sh`, `ci-local.sh`, `vm/macos/run-suite.sh`; default 2, or `NTFSMAC_LANES`) restores the strictly sequential order in plan order for debugging and timing comparisons; only full runs use the second lane (`--quick` and `--cases` never do). The second lane needs a second VM slot lock, taken for one concurrent phase at a time and released after it: it is only tried, never waited for (two runs that each hold one slot and wait for the other would never finish), and when it is not free the phase runs its lanes one after the other. Results are the same as sequential: every stage is recorded once in `stages.tsv` with its own duration and note, in plan order (`guest-build`, `integration`, `compat`, `daemon`, then the stress entries in the order of `test-all.sh --list-stress B`), never in completion order, with its own log `logs/<stage>.log` (concurrent stages write their log file only; the console shows a start line and an end line with the stage name and the time, and the last 15 log lines of a failed stage). A failing stage never stops the stage of the other lane; a lane that crashes is recorded as a failure (`lane-N`) and every stage it did not run as `not run`. Every stage owns its guest (`ntfsmac-<kind>-<PID of its script>`), scratch directory (`mktemp`), log and artifacts directory (`artifacts/<stage>`), so no two stages share a name, fixture copy or write path; the fixtures are only read, and the release build tree is brought up to date once by `run-suite.sh` before the stress phases (the stress suites each run `cmake --build` on it, a no-op then, so two never build at the same time). INT, TERM and HUP to `test-all.sh` are passed to `run-suite.sh`, which sends TERM to every running stage and all its descendants (their own traps delete their guests), waits for them, deletes any guest still named after one of those PIDs, releases the slots, and `test-all.sh` then writes the result with the stage `interrupted`.

| `macos-vm` | Environment B | Mount, integrity, stress, soak, performance and Finder tests (`test-all.sh --env B`) | Yes for the stages a milestone gate names |

`ci-local.sh` full mode runs, in order: `bootstrap`, `host`, `tsan`, `static-analysis`, `A`, `linux-build-test`, `fuzz-short`, `package`, `B`; `--only LIST` selects a subset. **Concurrency.** `bootstrap`, `host`, `tsan` and `static-analysis` (local builds, CPU heavy) run first, one after the other. Then two groups run at the same time, each in the order above: the Docker group (`A`, `linux-build-test`, `fuzz-short`, about 1200 s) and the VM group (`package`, then `B`). `package` takes a VM slot and runs one guest at a time (the build clone is deleted before the verify clone exists), and it ends before `B` starts, so `package` and `B` never overlap and together never hold more than the two slots of `vm/macos/run-suite.sh`; the Docker group uses no guest (Docker has its own VM). The Docker group overlaps only the first part of `B` (about 20 min of its 3200 s: `guest-build`, `integration` || `daemon`), not the stress phases with their deadlines and hang watchdogs. The host has 18 cores, Docker is allowed 16 and each guest has 4 vCPUs (B: 8 in two lanes), and `fuzz-short` runs up to three libFuzzer containers at once. To keep the guests their cores, every container of the Docker group gets `--cpus N` (`NTFS_LINUX_CPUS`, read by `vm/linux/run.sh`; `CI_LOCAL_DOCKER_CPUS`, default 4, `0` = no cap); the containers of `B` (fixtures, compat) and every stage before the groups run uncapped. Results do not change: each stage is recorded once with its own case id, the files are the same, the summary is in plan order (never in completion order), and the final `--verify-result` step runs after both groups have ended. A failing stage never stops the other group, nor the next stage of its own group; the exit status is 1 if any stage failed. A stage of the groups writes its output to its own log only (`ci-local: [D] start A (log ...)` and an end line with its time, the last 15 lines of a failed one); the logs follow whole, in plan order, after the groups end. INT, TERM and HUP to `ci-local.sh` create a stop file (no further stage of either group starts, also in the window before the second group has started) and start a sweeper that sends TERM to every process of both groups except the output filters of their pipelines (`tee`, `sed`, `awk`, `cat`, `tail`, `head`, `grep`, `tr`, `cut`, `sort`: a stage that is stopped writes its cleanup output through them, and a filter killed with it would make that a SIGPIPE); every second after that it signals only children of the groups that were not there before (a stage that started in the window of the signal), never again what a stopped stage starts itself while it cleans up (`release-local.sh` deleting its clone); a signal that arrives while the groups are being started only sets the stop file, and the sweeper starts once both groups exist. The stage scripts delete their guests and release their slots, the containers end because `vm/linux/run.sh` runs them with `--init --rm`. `ci-local.sh` waits for the groups and for every process the sweeper stopped (at most `CI_LOCAL_STOP_WAIT`, 300 s, then KILL), releases the slot that `package` holds (it is recorded under the pid of `ci-local.sh`), prints the summary (a stage that did not finish is `NOTRUN`) and exits 130 without the final verification (a result file that `test-all.sh` itself wrote is left as it is). Inside the groups `set -e` is suspended for a stage (`|| true`), as it was in every stage before: `own_stage` and `run_test_all` test each status themselves. The cap is clamped, with a warning, to the CPUs of `docker info`. `--serial` restores the old order for debugging and timing: no concurrency, no CPU cap, every stage alone with its output on the console; a selection that holds only one of the two groups (for example `--only host,B`) also runs without concurrency. It then checks every result file it wrote with `--verify-result --pre-commit`, requiring the environments of the selected stages and, for each, a `STAGE-<ENV>-*` case for every stage of that environment's `test-all.sh --dry-run` plan and for each stage `ci-local.sh` ran itself. Options that belong to another mode (`--quick` with `--dry-run`, `--only`, `--allow-dirty`, `--results-dir`, `--fuzz-seconds`; full-mode options with `--verify-result`) exit 2.

The tests of the checkers run in `ctest` (`tests/unit/ci/CMakeLists.txt`, audit M5-F08), so every `ci-local.sh --quick`, `test-all.sh --env host` and `linux-build-test` run executes them: `ci.local` (the options and exit codes of `ci-local.sh`, and quick mode with fake `cmake` and `ctest` on `PATH`: each failing stage must exit 1; `test_ci_local.sh --usage`, seconds, no build), `ci.local_full` (full mode and `--verify-result` with stub stages), `ci.gate_cases` (`gate_cases_check.py . M5`: every id of `tests/gate/M5.cases` has an emitter that can write it as pass), `ci.guest_sources` (`check_guest_sources.py .`: in each guest build script of `tests/integration/daemon`, the `tar` list that feeds the build directory holds every local header of the `.c` files on the `cc` lines, and each daemon header has its `.c` on the line; a self-test feeds it a known-bad script), `ci.guest_link` (`check_guest_link.py .`, macOS hosts only, skips with 77 elsewhere: untars each of those lists into a temporary directory and runs the `cc` lines that need no libntfs-3g or macFUSE, so a missing source or an undefined symbol fails on the host and not in the VM; link completeness, that is undefined symbols, is checked only by `ci.guest_link` on macOS, because `ci.guest_sources` checks includes and sibling files only) and the selftests of the result builders and classifiers that need no VM: `stress.soak_mixlib`, `stress.soak_result`, `stress.kill_result`, `stress.disconnect_result`, `stress.leaks_classify`, `perf.result`, `perf.report`. A test that cannot run says `SKIP: <reason>` and exits 77 (a ctest skip): `ci.local` and `ci.local_full` skip without a `git` binary (the Linux container has git and the whole repository, `.git` included, mounted at `/work`; `ci.local_full` runs git only in a throw-away repository it creates, `ci.local` only through `ci-local.sh`, which passes `-c safe.directory=*`, so root on a uid-501 mount gets no "dubious ownership" error), `stress.soak_mixlib` skips at run time with "SKIP: pgrep not installed", and both CI tests skip inside a `ci-local.sh --quick` run that a test started itself (`NTFSMAC_CI_NESTED`, so that the nested `ctest` does not run them again). The tests carry the label `ci` (`ctest -L ci`); `stress.soak_mixlib` and `perf.result` run serially (timing-sensitive). The three real build-and-ctest runs of `test_ci_local.sh` take two minutes and are registered only with `-DNTFSMAC_CI_BUILD_TESTS=ON` (`ci.local_build`); run them before changing `ci-local.sh` quick mode.

When to run: `ci-local.sh --quick` before every push, from the day T-M1-07 merges (it starts as bootstrap check, configure, build and `ctest`, and gains static analysis and the Linux stages as their tasks land; T-M5-08 completes it); the full run before each milestone gate and before a release. The result file for each run is committed under `tests/results/` (section 10), so every gate and release points at a recorded local run of the tested commit (section 10 defines the exact rule).

No test in the `macos-build` stage may attach or mount a disk image; that stage only builds and runs unit tests on the host.

Build outputs, packages and release candidates stay on the local machine under `build/` and `dist/` (both git-ignored). Publishing binaries anywhere is a later, explicit human decision.

`scripts/install-git-hooks.sh` installs a local `pre-push` hook that runs `ci-local.sh --quick`, so the "before every push" rule is enforced on this machine (`git push --no-verify` skips it once).

Local release pipeline: `scripts/release-local.sh` runs `ci-local.sh --quick`, then `packaging/build-pkg.sh` in a disposable clone of the golden VM (the engine links macFUSE's libfuse, which the host does not have), copies the unsigned package to `dist/<label>/`, and installs it in a second fresh clone: every installed binary must load and run, and `uninstall.sh` must leave no file and no receipt. Both VMs are deleted afterwards. Until T-M6-01 the package holds only the parts that exist (worker, ntfsprogs, probe, volmark under `/usr/local/libexec/ntfs-macos/`) and has no install scripts; see `packaging/README.md`.

## 10. Recording results

| Item | Rule |
|---|---|
| Result file | `tests/results/<UTC date>-<short sha>-<env>.json`, produced by `tests/harness/report.py` |
| Schema | `{ schema, git_sha, dirty_tree, env, host_os, guest_os, macfuse_version, ntfs3g_version, started, finished, cases: [ { id, status: pass/fail/skip/error, duration_s, evidence: [paths], note } ] }` |
| Dirty tree | A result from an uncommitted tree is marked `dirty_tree: true` and cannot satisfy a milestone gate. `test-all.sh` and `report.py aggregate` exit 3 (not 0) for a run in which every stage passed but the result is marked dirty (dirty tree at the start, HEAD or the tree changed by the end, or a sub-result from another commit), and `test-all.sh` prints "PASSED (dirty, not usable for a gate)"; 1 stays a failure and 2 a usage or write error. `ci-local.sh --only bootstrap` alone exits 1, like `--only tsan`: a file holding only own stages cannot satisfy the environment's plan stages, so select `bootstrap,host`. Evidence paths of the committed pre-M5 hand-written results (for example `2026-11-15-a983be6-host-unit.json` and `-A-unit.json`) are relative to the repository root, not to the result file, so the evidence check rejects them and they cannot be re-verified; there is no fallback. `ci-local.sh --allow-dirty` accepts 3 for a tree that was dirty at its start (the final verification rejects the files anyway); for a tree that was clean at the start, 3 fails the stage. Limit (M5-F12): the tree state is read at the start and at the end of a run only. An edit made during a run and reverted before its end is not seen, and neither is an edit that changes and restores a file between two reads. A check at each stage boundary would narrow the window and not close it (it would not cover the stages inside `vm/macos/run-suite.sh`, nor a change inside one stage); a gate run is therefore made on a tree nobody edits |
| "Result for the exact commit" | A result file cannot contain the SHA of the commit that adds it. `git_sha` is the commit that was tested (HEAD at the start of the run, clean tree). A gate or release commit G is covered by a result file when all of these hold: the file is valid (schema, no duplicate keys, no NaN), `dirty_tree` is false, no case failed or errored, at least one case passed, `STAGE-<ENV>-*` cases carry the file's own `env`; the file lies under `tests/results/`, is named `<date>-<sha7>-<env>[-...].json` for its own `git_sha` and `env`, and is committed unchanged in G together with every evidence path it names (the paths are relative to the directory of the file; `git cat-file -e G:<path>`, M5-F12); `git_sha` is G or an ancestor of G and the paths changed between them (`git diff-tree -r --no-renames`, so a rename counts as a change of both paths) are only in the one allowed set (`change_allowed` in `tests/harness/report.py`, shared with the fuzz campaign re-triage `campaign_result.retriage_bad`): `tests/results/`, `docs/audits/`, `CHECKPOINT.md`, `NEXT_ACTIONS.md`, `docs/SECURITY_FINDINGS.md` and `docs/UPSTREAM_REPORTS.md` (records and documents, any change), new files under `tests/fuzz/findings/` (a file that exists at the tested commit must be byte-identical at G: ctest and the campaign replay them) and rows appended to `tests/fuzz/campaign/known.tsv` (its content at the tested commit must be a byte prefix of its content at G: the fuzz-short stage reads it at run time and the first matching row wins; the unit tests of the classifiers use the frozen copy `tests/fuzz/campaign/testdata/known.tsv`), and the generated README status table, which must equal what `report.py readme` renders from the results of G. A classification commit after a campaign therefore does not invalidate the other results. For the gate environments the files together must also hold, per environment, a `STAGE-<ENV>-*` case with status `pass` for every stage of that environment's `test-all.sh --dry-run` plan and for each stage `ci-local.sh` runs itself (the table `OWN_STAGES` in `tests/harness/report.py`, used by full mode and by the check). In gate mode every `STAGE-*` case of every environment in the files must be `pass`. A skip is not accepted, with two exceptions that are skips by design: host `harness` and host `stress`. They are not copied into the checker: it reads them from `test-all.sh --env host --dry-run`, which prints a skipped stage as `[note]`, and the note in the result must match it exactly (for the host harness stage the note is "they drive the VM and the container: they run in --env B"). No other environment may skip a stage. Each file must be one of three kinds: a `test-all.sh` result with its own `STAGE-<ENV>-MODE` case (status `pass`, note `full`; the notes `quick`, `cases=...` and a missing record are rejected); a `-ci` file that holds only the own-stage cases; or an adopted criterion run (below). Each required environment still needs its full `test-all.sh` result: an adopted file is never a substitute for it.

*Criterion runs (M5-F04, M5-F05).* A stress suite or the fuzz campaign writes the plain criterion case ids (`S-SOAK-01`, `S-PAR-01`, `S-LEAK-01`, `S-KILL-01..05` with `S-KILL-RUN`, `S-DISC-01..05`, `F-CAMPAIGN-01`, and the `-CONTROL` cases) only when the run had the criterion parameters, judged by one predicate per suite next to the result builder: soak 6 h with the baseline at 1 h; parallel 30 min, 16 writers, hang limit at most 60 s; leaks at least 50 iterations; kill at least 20 repetitions of all four targets and a driver exit status of 0 or 1; disconnect at least 20 yanks per workload (`--full`) for all four workloads; fuzz a budget of 8 CPU-hours (28800 s) over all six targets on the patched engine. Every suite also needs its negative controls (`--controls ""`, `--no-control` and a disconnect/soak `--fault` make it no criterion run). Every other run, among them the short defaults that `test-all.sh --env B` runs, writes the same ids with the suffix `-SHORT` (`S-SOAK-01-SHORT`, `S-SOAK-01-CONTROL-SHORT`, ...) and records its parameters in the case note, so it cannot satisfy a criterion case. To record a criterion run: run the suite with its criterion options on a clean tree (commands in each suite README), then `python3 tests/harness/report.py adopt --env B --dir DIR` (`--env A` for the fuzz campaign). `adopt` refuses an invalid, dirty, sha-less, failed or `-SHORT` result and writes `tests/results/<date>-<sha7>-<env>-<suite>.json` with the evidence copied to `tests/results/evidence/<same name>/` and the paths rewritten. The file carries the one marker that only `adopt` writes: a `STAGE-<ENV>-MODE` case with status `pass` and the note `criterion:<suite>`. `adopt` writes one file per commit, day and suite: a second criterion run of the same suite on the same commit and day cannot be adopted (it refuses the existing name), so repeat it on another day or at another commit, or keep only the run that is to count. The commit in the result is the commit at the START of the run (each `run.sh` records `provenance.txt` first, then checks that its build tree was configured for this source tree and rebuilds it with `cmake --build`, so the host binaries come from that commit (soak, parallel, kill, disconnect); `adopt` also refuses a result whose `git_sha` differs from `provenance.txt` (a fuzz re-triage at a later commit leaves `retriage.txt` with both shas, which `adopt` checks) or that is older than it, so adopt the run's own `--out` directory as it is and do not copy it first (a copy changes the file times); a HEAD that moved or a tree that was dirty at the start or at the end marks the result dirty and `adopt` refuses it). The gate accepts such a file only when its other cases are exactly the plain criterion ids of that suite (and its run case), all `pass`, and its name ends in `-<suite>` (the table `CRITERION_SUITES` in `tests/harness/report.py`). Then commit the result and its evidence directory at (or after, within the allowed paths) the gate commit's tested commit and run the gate command. Performance runs (`tests/perf`) write the same format but are not adoptable: criterion 5.6 is judged by `tests/perf/report.py` (audit M5-F06). `ci-local.sh --fixtures DIR` records the skip "reusing DIR" for the fixtures stage, which the gate rejects (the images are not tied to the commit, audit M5-F07): such a run prints a warning at its start and cannot pass the gate. The cases listed in `tests/gate/<MILESTONE>.cases` must be present and `pass` (a skip or an absent case rejects); `--milestone` needs `--require-env host,A,B`. The parameters of the run are in the case ids (a plain id is written only at the criterion parameters, see above); the list itself checks presence and status. It does not cover the performance criterion 5.6 (`P-*`). Every id in it must be one that a real builder writes as `pass` (`tests/unit/ci/gate_cases_check.py`). The check is `scripts/ci-local.sh --verify-result <file>... --require-env host,A,B --milestone M5` (T-M5-08); `--require-case ID` adds single cases. The milestone audit repeats it. `--pre-commit` skips the path and committed-content checks, for the check `ci-local.sh` runs on files it has just written. |
| Extra stages of `ci-local.sh` | The stages that `ci-local.sh` runs itself have no `test-all.sh` result, so each environment gets one extra file `<date>-<sha7>-<env>-ci.json` (suffix `-ci`), built by `report.py aggregate` like any other: env `host` records `bootstrap`, `tsan` and `static-analysis`, env `A` records `linux-build-test` and `fuzz-short`, env `B` records `package` (cases `STAGE-HOST-BOOTSTRAP`, `STAGE-HOST-TSAN`, `STAGE-HOST-STATIC-ANALYSIS`, `STAGE-A-LINUX-BUILD-TEST`, `STAGE-A-FUZZ-SHORT`, `STAGE-B-PACKAGE`). The README status table takes the newest result per case, so these files do not hide the `test-all.sh` files. |
| Skips | A skipped case needs a `note`; skips are listed in the milestone audit |
| Pre-built inputs | `--deps-tar FILE` (the guest's NTFS-3G prefix) and `--fixtures DIR` (image files) carry a key that `scripts/run-inputs.sh` checks before a guest is cloned (fail closed: a different, missing or unreadable key refuses, no override). **Deps tar:** the key is `scripts/build-ntfs3g.sh --print-key` (pinned tarball digest, patch series, configure flags; computed for unset CFLAGS and LDFLAGS, which the guest builds run without) plus the layout (`dmn` for `dmn_vm.sh`/`attach_vm.sh` and the suites, `pkg` for `pkg_vm.sh`: the install prefix is not in the key, so a tar of one layout is refused by the other). It is sealed into the tar as `deps/.ntfsmac-deps-key` by the script that saves the tar, using the key read before the tree was copied to the guest; every member must be under `deps/`, and no link may be absolute or point outside it. Not covered: the golden image (macOS SDK, macFUSE headers, clang) and the host. The soak, parallel, disconnect, kill and perf entries check it too; the leak suite instead seeds from a tar and always runs `build-ntfs3g.sh`, which rebuilds when its stamp differs (its tar holds the build tree). **Fixtures:** the generators write `DIR/.fixtures-key`, one line per image they exported (name, sha256, key); a run names the images it uses and each must be listed with the current key and its current sha256 (an edited image, a missing one or one from an older export is refused). The key is the git tree hash of HEAD for the paths the generators read or run (`tests/fixtures`, `tests/tools`, `tests/stress/crashsweep`, `src`, `include`, `third_party/patches`, `third_party/deps.lock`, `vm/linux`, `scripts/build-ntfs3g.sh`, `CMakeLists.txt`, `cmake`; full list in `scripts/run-inputs.sh`). A dirty key never equals a clean one. It is unavailable outside a git checkout. The perf entry alone passes `--fixtures-unkeyed` to `dmn_vm.sh` (its one image is made by the run and is recorded by hash; any other suite refuses the flag). **Recording:** each suite takes its keys at the start and appends them to the start record `provenance.txt`, writes `inputs.txt` (deps tar sha256 and key, fixtures key, manifest of the images used), copies those lines into `meta.txt`, and adds a sentence to every case note; `test-all.sh --fixtures DIR` records the key and the manifest in the `fixtures` stage note and evidence (the stage stays a skip, which the gate rejects) |
| Performance explanations | An explanation in `docs/PERFORMANCE.md` is keyed to the run it was written for (`[run KEY]`: the `git_sha` of A and of B, 7 characters each, and 8 hex characters of the SHA-256 of the canonical JSON of both result files). `tests/perf/report.py` prints an entry with another key (or none, `unkeyed`) as "from run KEY, not re-confirmed", does not count it, and exits 1 while a phase above 2x has a placeholder or such an entry, while the parameters are smoke ones, or while A and B differ in `git_sha`, parameters or image, a tree was dirty or a case failed. A person confirms an entry by re-reading it and changing its key to the printed run key, in a commit that a reviewer sees |
| Evidence | Logs and small artifacts under `tests/results/evidence/<run>/`; images are not stored, only their hashes |
| Aggregated run | `scripts/test-all.sh` writes one file per run; each stage is a case `STAGE-<ENV>-<NAME>` and the harness cases are merged in, so the schema is unchanged. A merged result that is dirty or was made at another commit marks the aggregate dirty (case `STAGE-<ENV>-PROVENANCE`), as does a HEAD or tree change during the run. Evidence is moved into place only after the JSON is written |
| Status table | `README.md` section generated from the newest result per environment that has at least one case not `skip` (a skip-only result, such as `2026-11-14-3593b7c-B.json`, is ignored): each feature is `Verified (VM)`, `Verified (hardware)`, `Linux only`, `Partial (VM)` (some matching cases passed, the rest skipped), `Failing (VM)`, `Failing (Linux)` (a failure is shown before any pass, hardware included) or `Untested`; `Verified (VM)` needs every matching case to pass; generated between the `status-table` markers by `python3 tests/harness/report.py readme` (`--check` exits non-zero when stale: a manual and gate step, deliberately not a unit test, because it goes stale whenever a result lands); the table names no result file but shows the commit of the newest result per row, so every committed result that changes a row's commit or state makes it stale and the table must be regenerated in the same commit; results and hardware files whose commit is not an ancestor of `HEAD` are left out, so a squash or rebase workflow that rewrites the tested commits turns the committed results into non-ancestors and empties the rows; `-SHORT` runs never count; the feature-to-case mapping is `tests/harness/features.json`; per case, the newest clean-tree result that is not a skip counts |
| Hardware runs | `tests/results/hardware/<UTC date>-<sha7>.md`, written from the protocol, with device serial numbers and the human's confirmation. `report.py` ignores a file with another name and one whose commit is not an ancestor of `HEAD` |
| Flaky tests | A test that fails once and passes on retry is recorded as `fail` with a note, and gets a task; no silent retries |
