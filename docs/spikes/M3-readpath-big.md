## Decision

**No change to the product options for reads or large files.** No read at, across or past EOF failed in any case (I-READ-01..07, B and A), and files of 4 GiB + 1 byte and 5 GiB write, hash, update and truncate correctly. Criteria 3.5 and 3.8 are met for B. **Open limits:**
- a write past EOF without a preceding `ftruncate` fills the gap with zeros on disk in B (Linux makes a hole), so a sparse file has to be made with `ftruncate` first (finding 9);
- updating a compressed file stores the touched 64 KiB unit uncompressed (finding 13).

The golden VM has only about 7 GiB free, so the 4 GiB and 5 GiB cases skip on it; `run-env-b.sh` needs a larger guest disk (proposal 1).

## Findings: read path (T-M3-07)

1. **Reads at and past EOF never fail and never reach the worker.** `pread` for every size in 0, 1, 511, 512, 4095, 4096, 4097, cluster-1, cluster, cluster+1 and 1 MiB+1, at offsets 0, 1, n-1, n, n+1, n+511, n+4096, n+64 KiB, n+1 MiB, 2^32 and 2^40, with lengths 1 B to 1 MiB, returns exactly `data[off:off+len]` (empty at and past EOF), with and without the page cache (`F_NOCACHE`), right after writing and after a remount. `read(2)` loops with 4 KiB to 8 MiB buffers end with an empty read, and three more reads at EOF are empty (I-READ-01).
2. **The empty-reply path is not reached.** With `-o debug` (I-READ-05) 103 FUSE_READ requests for seven file sizes (and a reader whose file is truncated under it) show no request at or past EOF, no empty reply (outsize 16) and no error. A zero-length file gets no FUSE_READ at all. The macFUSE side answers reads at and past EOF from the file size it holds, so NTFS-3G is never asked; the "no empty reply to a non-EOF read" rule holds because NTFS-3G always returns the bytes it has.
3. **What the backend asks for and gets (short reads).** The request for a file below one page starts at offset 0 and its length is the file size rounded up to 512 bytes (1 B file: `512 bytes from 0`, driver returns 1, reply outsize 17; 511 B: 512 requested, 511 returned; 4095 B: 4096 requested, 4095 returned; 4097 B: 4608 requested, 4097 returned). The last block of a 1 MiB + 1 file is asked as `512 bytes from 1048576` and answered with 1 byte. So a short reply at EOF is the normal case on this backend and is accepted. Larger reads come as 16 KiB, 64 KiB, 80 KiB and 1 MiB requests answered in full; replies of 64 KiB and more carry `outsize: 24` (the data does not travel inline in the reply; 16 KiB replies do).
4. **User-level short reads:** `read(2)` into a buffer larger than the rest returns the rest in one call (1 MiB + 1 file, 8 MiB buffer: one read of 1048577), and a file of 10 MiB returns 8 MiB and then 2 MiB for an 8 MiB buffer. Linux gives the same sizes (I-READ-01, 04, 06).
5. **Truncate while open:** a descriptor opened read/write, truncated by `ftruncate` to 0, 1, 100, cluster-1, cluster, cluster+1 or half of a 200 B to 1 MiB + 1 file, reads exactly the new content; reads at and past the new EOF are empty, `fstat` shows the new size, a second descriptor agrees, growing by `ftruncate` gives zeros, a write after that reads back (I-READ-02, 56 cases, cached and not).
6. **Truncated by another descriptor** (`truncate(path)`, `open(O_TRUNC)`, `ftruncate` on a second descriptor) while a reader is open at or beyond the new EOF: the next `read` is empty (never EIO), the reader's `fstat` shows the new size, and when the writer extends the file again the reader sees the new bytes from its offset (I-READ-03, 42 cases). With `-o debug` a reader of a file truncated to 100 B under it sends `512 bytes from 0` and gets 100 bytes (I-READ-05).
7. **Resident data:** a new file stays in the MFT record up to 640 bytes (largest resident size among 0..960 in steps of 64) and is non-resident from 704 bytes. Residency read from the unmounted image (`readlib.disk_view`). The same limit on Linux. Reads of resident and non-resident files are identical at every edge (I-READ-01, 04).
8. **Transitions:** a 100 B resident file grown by a write at 4900 becomes non-resident (5000 B, 8192 allocated); truncated to 50 it stays non-resident; truncated to 0 and rewritten with 30 B it is resident again; `ftruncate` of the 30 B file to 10 MiB makes a non-resident sparse file with initialized size 30; appends of 300 B x 4 then 4096 B read back correctly at every step. Every state reads correctly cached and not (I-READ-04).
9. **Other read paths:** `readv` across EOF, `pread` with buffers up to 64 MiB, `mmap` of files of 1 B to 5 MiB + 7 (the last page ends inside the file), `cat`, `dd` with 4 MiB and 1 B blocks, `cp`, `head -c` and `tail -c` all return exact content, warm and after a remount (I-READ-06). Volumes with 512 B and 64 KiB clusters give the same (I-READ-07).

## Findings: large and sparse files (T-M3-09)

10. **Sizes 0 B, 1 B, cluster+/-1, 1 MiB+/-1, 64 MiB + 1 and 128 MiB** write, hash equal, remount, hash equal, `$DATA` size on disk equal, `ntfsfix -n` exit 0 (I-BIG-01, also on Linux).
11. **4 GiB + 1 byte and 5 GiB files work.** Written in 1 MiB writes at about 600 MiB/s (guest, image on the guest SSD); full-file hash after write and after remount equals the expected hash (read speed 1.7 to 1.8 GiB/s); `pread` at 2^31 - 1 .. 2^31 + 1, 2^32 - 1 .. 2^32 + 1, size - 1, size and past gives the expected bytes (cached and not); updates of 1 MiB + 7 B across 2 GiB, 64 KiB across 4 GiB, the last byte, the first bytes and 100 KB in the middle read back equal after a remount; truncate to 2^32 - 1 (4 GiB + 1 file) or 2^32 + 12345 (5 GiB file) and growth by 1 MiB + 9 give the expected hash; `ntfsfix -n` exit 0 after every phase (I-BIG-02, I-BIG-03, 55 to 65 s each).
12. **A truncate that grows a file makes it sparse.** After `ftruncate` up, the file has the SPARSE flag (0x200), a compression unit of 16 clusters and the zero tail as a hole (on disk: 4 GiB data size with the compressed size 4 GiB and the grown 1 MiB as a hole). A resident 30 B file grown to 10 MiB becomes non-resident and sparse. Reads of the hole return zeros.
13. **Sparse files keep their holes** (I-BIG-SPARSE-01, 256 MiB files made by `ftruncate` then writes of 1 MiB + 4099 B): hole at start, middle, end and all hole give the expected hash; `st_blocks` is about 1.0 MiB, 2.0 MiB, 1.0 MiB and 0 for about 1, 2, 1 and 0 MiB of data (allocation is in units of 16 clusters, 64 KiB); on disk the file has FILE_ATTRIBUTE_SPARSE_FILE, a non-resident `$DATA` with the sparse flag, compression unit 2^4 and a compressed size equal to `st_blocks` (`ntfsinfo -F` output in the evidence); everything the same after a remount., Linux gives the same layout with a slightly smaller allocation (1056768 against 1064960 bytes for the one-piece files).
14. **A 6 GiB sparse file** with data below, across and above 4 GiB (I-BIG-SPARSE-02): hash of 6 GiB in 2.8 s, `st_blocks` 352 KiB for 298 KiB of data, same after a remount.
15. **Updates of sparse files:** a write of 100 KiB + 3 into the middle hole raises `st_blocks` by 112 KiB; a 5000 B overwrite inside data changes nothing; a 1 B write into a hole allocates 16 KiB; 64 KiB of zeros written into data stay allocated; grow by 10 MiB and shrink into the former hole keeps the file sparse; two single-byte writes into an all-hole file make 32 KiB of `st_blocks` in B (8 KiB on Linux). All hashes equal (I-BIG-SPARSE-01).
16. **Write past EOF is dense in B.** `pwrite` of 1 byte at 64 MiB into an empty file (no `ftruncate`) gives `st_blocks` 64 MiB, no sparse flag, 64 MiB of zeros on disk. On Linux the same sequence gives `st_blocks` 4 KiB. Make sparse files with `ftruncate` first. (I-BIG-SPARSE-01, `seek_write`.)
17. **`SEEK_DATA` and `SEEK_HOLE` are not hole-aware:** `lseek(fd, 0, SEEK_DATA)` returns 0 and `SEEK_HOLE` returns the file size, also for the all-hole file, in B and on Linux. `fcntl(F_PUNCHHOLE)` returns ENOTTY in B. Recorded, not asserted.

## Findings: compressed files made on Linux (I-BIG-COMP-01)

18. **Compressed files made on Linux read back equal in B.** Linux marks a directory with `system.ntfs_attrib_be` 0x830 (bit 0x800), creates 8 files in it (2 MiB of text, 1 MiB random plus 1 MiB zeros, 1 MiB random, 100 B, 1 B, empty, 20 MiB of text, one in a subdirectory) and one plain file beside it. Linux compresses them all (`st_blocks` 12% for text, 50% for the half-zero file, 100% for random data, files of 100 B and less stay resident). B reads every file with the same size, SHA-256 and `st_blocks`; the compressed flag shows as 0x820 in `system.ntfs_attrib_be`, and B shows the directory as 0x830.
19. **B can update compressed files.** Overwrite in the middle, append, truncate down and up, rewrite from `O_TRUNC`, write into a 1 B and an empty file, rename, unlink, and new files in the compressed directory (also with `nocompression`) are all accepted; each file read back is exactly the expected content (no refused or half-done operation). `nocompression` is the NTFS-3G option for this (existing compressed files are still read and updated, new files are plain).
20. **A compressed file is rewritten less compactly after an update.** A 4 byte overwrite in a 64 KiB text file (8 KiB allocated) leaves it 64 KiB allocated (the unit is stored uncompressed); a 70000 byte overwrite in a 2 MiB text file (256 KiB) gives 368 KiB. No data is lost, only space. The compressed flag stays on the file.
21. **New files in a compressed directory are compressed in B** (compression is the NTFS-3G default): a 1 MiB text file is compressed to 128 KiB, a subdirectory made in B is marked and its file is compressed; with `nocompression` a new file in the same directory is plain (524288 bytes, 524288 allocated, no flag), and a file beside the directory is plain either way.
22. **Linux reads the guest's final image** (A-after-B): every file equal to the state the guest left (SHA-256 and size), compressed flags where B left them, `ntfsfix -n` exit 0 at all hops, and Linux can append to a compressed file written by B and read it back. `ntfsfix -n` is clean.

## Not covered
- Encrypted (EFS) files; compressed files larger than the 20 MiB used here; `nocompression` effect on files that B compresses itself for a long run.
- Hard-link counts, timestamps and xattrs of large files (other suites).
- Memory-mapped writes to large files (T-M3-11).
- 5 GiB written on Linux and read in B (the large files are made and read in B; only I-BIG-COMP-01 crosses environments).
