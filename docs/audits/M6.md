## 0. Verdict

**Defect list, not a signed note. Criterion 6.7 is done as an audit, and its result is that the M6 exit gate cannot be closed yet: one High finding must be fixed first, and the evidence for 6.1, 6.2, 6.3 and 6.5 must be re-made at a clean commit and committed.**

The root scripts are written with care. They use absolute program paths, a fixed `PATH` and `umask`, no environment variable and no argument but `$3`, and no temporary file outside a root-only directory. They delete only below directories that `root_only_dir` accepts (the physical path is the logical path, and every directory above is root-owned and not writable by group or others). The manifest is the one list for the payload, the preflight, the installed set and the uninstaller, and lints keep them in step. Under these rules I found no string from a user, a disk or a file name that root runs. Two gaps remain in what root installs and deletes:

- The guard that refuses an install below a directory a user can change follows the *physical* chain of each installed path. A user who owns `/usr/local` can put a symbolic link at `/usr/local/libexec` that points to a root-only directory. The walk then never looks at `/usr/local`, the install goes ahead, and the user can later replace what launchd runs as root (M6-F01, High; `dev-install.sh` has the same check).
- One package of the earlier layout was published (pre-release `v0.1.0-dev.20261116`, two downloads of the `.pkg`). Its receipt lists `usr/local/share/doc/ntfs-macos/*`. On an upgrade, preinstall leaves those files when the directory is not root-only, and the macOS Installer then deletes them itself, as root, as obsolete files of the old receipt. A user who owns `/usr/local/share/doc` (a Homebrew from an Intel Mac) can put a link there and point that deletion at another directory. A preinstall guard is needed (M6-F02, Medium).

The evidence is the other gap. The only committed M6 run log is the I-PKG-03/04 log of a package built from a dirty tree at `63ff4ef`, before the scripts were committed and before `a258428` changed `build-pkg.sh`. I-PKG-05, -06 and -07 have no log; the reproducibility result exists only as README text about a dirty tree; no real source archive was recorded; no file under `tests/results/` covers an M6 case (M6-F03, Medium).

Finding counts: Critical 0, High 1, Medium 2, Low 5.

## 1. Findings

### High

**M6-F01. The root-only check of preinstall (and of `dev-install.sh`) skips the directory that holds a symbolic link on the way to an installed path** (`packaging/scripts/preinstall:176-199`, the walk starts at `r=$(cd -P -- "$d" && pwd -P)`, `:183`; `packaging/dev-install.sh:136-153`, `:141`; the warning loop of `packaging/uninstall.sh:161-183` has the same shape).
Step 5 takes the deepest existing directory above each installed path, resolves it with `cd -P` and walks up the *physical* path. Step 4 refuses a link only at a manifest path itself (`/usr/local/libexec/ntfs-macos`, not `/usr/local/libexec`). So when `/usr/local/libexec` is a link, the walk checks the link's target and its parents, but never `/usr/local`, where the link lives. The comment at `dev-install.sh:132-136` states the threat this check exists for: "A user-owned /usr/local/libexec ... would let a user process rename the directory and plant a binary".
Scenario (the walk was reproduced in `<tmp>` with the lines of step 5 and a tree `F/usr/local/libexec -> F/opt/libexec`; it checked `F/opt/libexec`, `F/opt`, `F`, its parents, `F/Library/...`, and never `F/usr/local` or `F/usr`): on a Mac where a user owns `/usr/local` (an old `chown -R` for Homebrew), that user creates `/usr/local/libexec -> /private/var/db` (any root-only directory) before the install. Preinstall passes. The Installer writes `ntfs-macos/` below the link, or replaces the link with a directory; I did not check which in a VM. In both cases the package is now installed below a directory the user owns, which is exactly the state step 5 refuses for a real directory: the user renames or repoints `/usr/local/libexec` and puts a directory with their own `ntfs-macos/ntfsmacd` in its place. launchd runs `/usr/local/libexec/ntfs-macos/ntfsmacd` as root at the next load (`integration/launchd/org.ntfs-macos.ntfsmacd.plist`, `ProgramArguments`). The daemon then runs the worker, the probe and volmark from the same directory. Precondition: a user-writable `/usr/local`, which is rare on an Apple silicon Mac, but is the case the guard is written for and the one I-PKG-05 tests for `/usr/local/libexec` (`pkg_preflight_vm_guest.sh:256-258`).
Fix: in step 5 (and in `check_ancestors` and the uninstall warning), walk the *logical* path from the installed path up to `/`, and for each existing component refuse when it is a symbolic link (`[ -L ]`) or when it is not root-only, in the same way as `root_only_dir` (which already requires that the physical path equal the logical one). No manifest path lies below a system link (`/var`, `/tmp`, `/etc`), so no exception is needed. Add the case "user-owned `/usr/local` with `/usr/local/libexec` a link to a root-only directory" to I-PKG-05 and to the `dev-install.sh` refusals of I-PKG-01 (i). As defence in depth, the daemon could check at start that the directory chain of its own executable is root-only and refuse to spawn programs otherwise.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* One function `root_only_chain` walks each path from `/` down with `[ -L ]` on every component and checks the owner and mode of every real directory; `root_only_dir` and the refusals use it. It is one text in preinstall, postinstall, `uninstall.sh` and `dev-install.sh` (a package script cannot source a repository file); U-PKG-08 (`packaging.root_only`) keeps the copies equal, runs the cases on a real tree and fails each mutant. I-PKG-05 and I-PKG-01 have the link case with a root-owned and a user-owned `/usr/local`. The daemon's own check of its directory chain is not done (owner decision 1 still open).

### Medium

**M6-F02. On an upgrade from the published pre-release, the macOS Installer deletes as root the old receipt's files in `/usr/local/share/doc/ntfs-macos`, a directory a user may control** (`packaging/scripts/preinstall:218-264`; `tests/integration/packaging/pkg_preflight_vm_guest.sh:182`; `docs/INSTALL.md:85-86`; `packaging/README.md:183-187`).
Distributed old layout: `gh release list --repo kurok/ntfs-macos` shows one release, the pre-release `v0.1.0-dev.20261116` (2026-11-16), with the asset `ntfs-macos-0.1.0-dev.20261116.g91358db1a2ed.pkg` (downloaded 2 times; sha256 `f6e8bcda...e68`, the same as `docs/releases/0.1.0-dev.20261116.md` and as the copy in the main checkout's `dist/`). Its identifier is `org.ntfs-macos.pkg`, the same as today. `lsbom` of that package lists `./usr/local/share/doc/ntfs-macos/{COPYING,README.md,BUILD-INFO}`, `LICENSES/{GPL-2.0-or-later.txt,LGPL-2.1.txt,LicenseRef-macFUSE-notice.txt,README.md}` and AppleDouble `._` copies of five of them, plus `./usr/local/libexec/ntfs-macos/._uninstall.sh`. The current package ships none of these.
What happens on the upgrade: preinstall removes them itself only when `root_only_dir` accepts the directory (`:236`); else it leaves them and logs a line. The project found that the Installer then removes obsolete files of the old receipt itself, as root, also in a user-owned directory (`pkg_preflight_vm_guest.sh:182`, recorded only as a NOTE, for `/usr/local/bin/ntfsmac`). The Installer's own deletion is outside every guard of preinstall.
Scenario: a Mac with the pre-release installed and a user-owned `/usr/local/share/doc` (Homebrew from an Intel Mac owns `share/doc`). The user renames the root-owned `ntfs-macos` directory in their own `share/doc` and puts `ntfs-macos -> /some/root/directory` in its place (or a link at `ntfs-macos/LICENSES`). Then an administrator installs the current package. Preinstall sees the link and leaves the files (`root_only_dir` fails). The Installer then unlinks `/usr/local/share/doc/ntfs-macos/COPYING` and the other names. `unlink(2)` follows a link in a parent component, and nothing in the repository shows that the Installer refuses it; I did not check this in a VM. Effect: root deletes files named `COPYING`, `README.md`, `BUILD-INFO`, `GPL-2.0-or-later.txt`, `LGPL-2.1.txt`, `LicenseRef-macFUSE-notice.txt` and their `._` names in a directory the user chooses, and may remove empty directories there. That is data loss or a denial of service, not code execution, because the names are fixed. The old `uninstall.sh` of that pre-release (installed at `/usr/local/libexec/ntfs-macos/uninstall.sh`) has the same flaw: it runs `rm -f "/$f"` on each receipt path with no check of the directory (`git show 91358db:packaging/uninstall.sh`).
Is a preinstall guard needed: yes. A check in preinstall alone cannot close it, because the user can plant the link after preinstall has run and before the Installer deletes (the directory is theirs). The deletion must not happen at all. Options: (a) give the new layout another package identifier (for example `org.ntfs-macos.pkg.v2`; the Installer then has no old receipt of the same identifier to compare), and let preinstall remove what it safely can from the old receipt and `pkgutil --forget` it; (b) keep the identifier and have preinstall `pkgutil --forget org.ntfs-macos.pkg` after its own clean-up, but only if a VM test shows that the Installer reads the old receipt after preinstall, not before; (c) refuse the upgrade when the old receipt lists a path outside the root-only regions that is still there, and tell the user to remove it by hand. Whatever is chosen, turn the NOTE at `:182` into a check, add the case "old receipt with `share/doc` paths, user-owned `/usr/local/share/doc`, `ntfs-macos` replaced by a link to a directory with a canary file" to I-PKG-06, and assert that the canary survives. Also add a warning to the pre-release notes that its `uninstall.sh` must not be run on a Mac where `/usr/local/share/doc` is user-writable; whether to withdraw or supersede that pre-release is an owner decision.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* Owner decision 2026-11-26: option (a), a new identifier `org.ntfs-macos.pkg.v2` (`packaging/README.md`, "Package identifier"). preinstall removes the old receipt's files only below a root-only chain and forgets the old receipt when none is left; otherwise it keeps it and names `uninstall.sh --old-receipt`. The NOTE of I-PKG-06 is now a check, and I-PKG-06 `--case oldrel` installs the published pre-release (local copy, sha256 checked) before this package, with a canary behind a link in a user-owned `/usr/local/share/doc`. The pre-release notes and its withdrawal are not changed here.

### Low

**M6-F04. The current `uninstall.sh` refuses to remove the published pre-release, although its header and the README say it removes a package of the earlier layout** (`packaging/uninstall.sh:17-20`, `:197-221`, refusal at `:218`; `packaging/README.md:265-270`; `docs/INSTALL.md:170-171`).
The receipt check accepts a receipt path only below a `dir` of the manifest or equal to a `file` or `link`. The published package's receipt has `usr/local/share/doc/ntfs-macos/*`. Fed with the files of that package, the check stops at `/usr/local/share/doc/ntfs-macos/._COPYING` ("refusing receipt path outside the directories of the manifest"; reproduced in `<tmp>` with the lines of the script). It fails closed, so it is not a safety defect. But the only way left to remove the pre-release without upgrading is its own `uninstall.sh`, which has the flaw of M6-F02.
Fix: accept the known old regions (`/usr/local/share/doc/ntfs-macos/...`) in the receipt check, and remove those files only when `root_only_dir` accepts their directory, as preinstall does; else keep and name them. Correct the header, the README and INSTALL.md to say what is supported.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* `uninstall.sh` accepts, for the receipt `org.ntfs-macos.pkg` only, the exact files the pre-release put in `/usr/local/share/doc/ntfs-macos`, removes them through the same per-path check and removes only the directories `ntfs-macos` and `ntfs-macos/LICENSES`; `--old-receipt` removes only the earlier layout. Header, README and INSTALL.md say so.

**M6-F05. `uninstall.sh` deletes below a directory that is not root-only after only a warning** (`packaging/uninstall.sh:161-183`, warning; `:249-257` and `:288-295`, `rm -f` with no directory check; `:105`, the only link check, made once at the start).
Preinstall and `dev-install.sh` follow the rule "root does not delete in a directory a user can change" (`remove_old`, `root_only_dir`). The uninstaller prints `WARNING: ... is not root-only` and then removes the receipt's and the manifest's files anyway. If the install-time state has changed (a later `chown` of `/usr/local/libexec`, or the M6-F01 situation), a user can swap `/usr/local/libexec/ntfs-macos` for a link after the check at `:105` and before the `rm -f` calls. Root then unlinks files with the project's fixed names (`ntfsmacd`, `mkntfs`, `manifest.txt`, ...) in a directory the user chooses. The names are fixed and the window needs a race, so the effect is small.
Fix: apply `root_only_dir` to the directory of each file before `rm -f`, and keep and name the file otherwise, as preinstall does; or refuse the whole run when the warning fires and ask the administrator to fix the ownership first.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* Both: before any change `uninstall.sh` checks every manifest path and stops with nothing removed (issue #6); with `--allow-unsafe-ancestors` every removal (`rm -f`, `rm -rf`, `rmdir`) still goes through `may_remove`, which keeps and names a path below a directory that fails the check, keeps its receipt and makes the exit status 1.

**M6-F06. Refusal messages put a path that a user can name into a command line for the administrator to paste** (`packaging/scripts/preinstall:191`; `packaging/dev-install.sh:147`).
The message ends with `Fix it first: sudo chown root '$r' && sudo chmod go-w '$r'`, where `$r` is the physical path of a directory above an installed path. With a link (M6-F01) or a user-owned parent, that name comes from the user, and a name with a `'` turns the suggested command into another command run with `sudo` by whoever copies it from `/var/log/install.log`. This needs a person to paste it, so it is Low.
Fix: do not build a shell command from a path. Name the directory and the required owner and mode in prose, or refuse to print a path that holds a quote or a control character.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* The refusals name the directory through `ro_show` (in double quotes, each character other than letters, digits, space and `/ . _ , : @ + = -` shown as `?`) and say in words what to change; U-PKG-08 checks that no root-run script suggests `sudo chown` or `sudo chmod`.

**M6-F07. The owners and modes in the built package's bill of materials are never compared with the manifest on the host** (`packaging/payload-check.sh:25-53`; `packaging/build-pkg.sh:334`, `:349`).
`payload-check.sh` compares path lists only. U-PKG-03 compares the modes of the `--plan` output, not of a built package. The modes and owners of the real package are checked only after a VM install (I-PKG-03 "with its owner, group and mode"). A regression in staging (`install -d -m`, `chmod`) or in `pkgbuild --ownership` would pass `build-pkg.sh` and appear only in a VM run, which no stage runs (M6-F03). `sign-and-notarize.sh` already does the right check between two packages (`lsbom -p MUGf`).
Fix: in `build-pkg.sh`, after `pkgbuild`, compare `lsbom -p MUGf` of the component Bom with the manifest's `dir`/`file` entries (mode, `0/0` or `root/wheel`, path), with the shared parents as `0755 root wheel`, and fail on any difference.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* `packaging/bom-check.sh`, run by `build-pkg.sh` after `pkgbuild` on `lsbom -p MUGf` of the expanded component; U-PKG-09 (`packaging.bom_check`) builds small packages with `pkgbuild` and fails on `--ownership preserve`, wrong modes, an extra or missing file and list mutants.

**M6-F08. Two root-run scripts are linted at error severity only** (`tests/unit/packaging/CMakeLists.txt:65-66`, `packaging.shellcheck_errors`, `-S error`, on `uninstall.sh` and `dev-install.sh`).

Nothing found is a defect, but the check that would find the next one is off for a root script.
Fix: move `uninstall.sh` to `packaging.shellcheck_release` (all severities) after quoting `"$job"` and naming the unused fields `_`; do the same for `dev-install.sh` or record why not.
*Fixed in: the change on top of `c294f65` that closes issue #6 (commit to be filled in when it is merged).* Done for both: `"/Library/LaunchDaemons/$job.plist"` quoted in `uninstall.sh` and `dev-install.sh` (both places), the unused fields read as `_`, and both scripts moved to `packaging.shellcheck_release`.

## 3. Package contents and the manifest

No package of the current layout exists in any `dist/` directory: the main checkout's `dist/` holds `0.1.0-dev.20261115.g002ab4d16173.dirty` and `0.1.0-dev.20261116.g91358db1a2ed` (the published one), both of the earlier layout; the worktrees hold none. ## 4. The uninstall manifest

## 7. The signing script, judged without credentials

What is right: credentials come only as arguments and are passed only to `codesign`, `productsign` and `notarytool`; no `security`, no keychain read, no environment (U-PKG-05 asserts it never prints `security`). Swapped identities are refused by their prefix. Every Mach-O of the payload is found with `file -b` per path and signed with `--options runtime --timestamp`; only programs that link `/usr/local/lib/libfuse*` get `com.apple.security.cs.disable-library-validation`, and the script stops if none does. The component is rebuilt with `pkgbuild --ownership recommended` and the original scripts, identifier, version and Distribution, then `lsbom -p MUGf` must equal the original's, which catches the `._` files and the uid problem of `--flatten-full`. `notarytool submit --wait` must report `status: Accepted` and the log is printed otherwise; `stapler staple`, `stapler validate` and `spctl -a -t install` run under `set -e`, so a rejection stops the script. The source archive is checked against its `SHA256SUMS` line before it is copied. The input directory is not changed, and the scratch directory is `mktemp -d` with an EXIT trap.
What cannot be judged here, and should be checked in the first real run in a disposable guest before anything is published (the README says the same for the first two):
1. that the worker, signed with the hardened runtime and the entitlement, loads macFUSE's libfuse and mounts;
2. that the Developer ID signed CLI agrees with the cdhash requirement that postinstall records (postinstall reads the CLI as installed, so it should);
3. that `ntfsmacd`, the probe, volmark and the ntfsprogs still run under the hardened runtime (sandbox-exec, `launchctl asuser`, `DYLD_*` use);
4. that `notarytool log` shows no warnings for an Accepted submission (the script fetches the log only on failure);
5. that the re-signed package passes I-PKG-03/04 unchanged, since every cdhash differs from the unsigned build and the reproducibility result of 6.2 applies to the unsigned package only.
I found no defect in the script itself.
